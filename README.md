# 小程序云开发教程：从初始化到部署上线，跑通云托管并避开基础库版本与冷启动的坑

小程序云开发教程的核心流程可以概括为四步：开通云托管环境、在小程序里初始化 `wx.cloud`、用 `callContainer` 调用服务、把代码部署上线。全程不需要买服务器、备案域名或配置 HTTPS 证书，这也是它比传统后端开发省事的地方。

## 小程序云开发和传统后端开发有什么区别？

云开发把服务器、数据库和微信鉴权都托管了，小程序前端直接调用云端服务，不用自己维护服务器、域名和证书。

微信云托管支持 Java、PHP、NodeJS、Python、Go 等语言，并提供 Spring Boot、Express、Django、Laravel 等框架模板，现有项目基本可以平滑迁上去。网关层支持 HTTPS 和 WebSocket，自带防 DDoS、防数据爬取能力，微信用户就近接入。

对个人开发者最直接的好处是省掉两件事：国内域名备案和 HTTPS 证书。小程序要求后端必须是 HTTPS，自己买服务器的话这是一笔额外开销和一堆配置工作；云托管不用买证书，小程序可以直接调用。

调用走的是内网，不消耗公网流量，后端还能直接拿到 openid 和 unionid，不用自己维护 access_token。如果服务只给自家小程序用，建议在服务设置里关闭公网访问——其他人即使拿到环境 ID 和服务名也进不来。

## 开始之前要准备什么？

需要三样东西：一个微信小程序账号、开通云托管功能、把小程序基础库版本升到 2.23.0 及以上。

前两样按控制台提示操作即可。第三个是第一个高频坑：`wx.cloud.callContainer` 要求小程序基础库版本在 2.23.0 及以上，光本地调试通过不够，还要去「小程序管理后台」-「设置」-「功能设置」-「基础库最低版本设置」里，把最低版本设成 2.23.0 或更高。漏掉这一步，部分用户的小程序端会直接调不通，而且报错信息不一定直观。

## 小程序云开发怎么初始化？

初始化只需要在 app.js 的 `onLaunch` 里执行一次 `wx.cloud.init()`，之后全局都能用。

如果小程序访问的是自己账号下的云托管环境，直接这样写：

js
App({
  async onLaunch() {
    wx.cloud.init()
    const result = await wx.cloud.callContainer({
      config: {
        env: 'prod-01', // 云托管环境 ID
      },
      path: '/',
      method: 'GET',
      header: {
        'X-WX-SERVICE': 'xxx', // 服务名称
      },
    })
    console.log(result)
  }
})


资源复用的情况要换一种写法。比如小程序 B 要访问小程序 A 的云托管环境，需要指定环境所属账号的 appid：

js
const c1 = new wx.cloud.Cloud({
  resourceAppid: 'WXAAA', // 环境所属的账号 appid
  resourceEnv: 'prod_001', // 云托管的环境 ID
})
await c1.init()


同主体的小程序和公众号之间可以直接配置资源复用；不同主体的话，官方推荐用微信开放平台的第三方平台方式，或者把对方当作「其他客户端」走公网访问。后一种方式下，对方用不了云调用，还需要在小程序后台配置服务器域名。

## callContainer 怎么调用才不容易出错？

调用本身不复杂，关键是处理 `init` 异步完成前的时序问题。官方给的封装方案是带重试的 `call` 方法，核心逻辑并不难理解。

js
async call(obj, number = 0) {
  const that = this
  if (that.cloud == null) {
    const cloud = new wx.cloud.Cloud({
      resourceAppid: 'WXAAA',
      resourceEnv: 'prod-001',
    })
    that.cloud = cloud
    await that.cloud.init()
  }
  try {
    const result = await that.cloud.callContainer({
      path: obj.path,
      method: obj.method || 'GET',
      header: {
        'X-WX-SERVICE': 'xxx',
      },
    })
    return result.data
  } catch (e) {
    const error = e.toString()
    if (error.indexOf("Cloud API isn't enabled") != -1 && number < 3) {
      return new Promise((resolve) => {
        setTimeout(function () {
          resolve(that.call(obj, number + 1))
        }, 300)
      })
    } else {
      throw new Error(`微信云托管调用失败${error}`)
    }
  }
}


几个容易忽略的参数细节：

- `config.env` 填云托管环境 ID，必填
- `header` 里的 `X-WX-SERVICE` 填服务名称，在「微信云托管 - 服务管理 - 服务列表」里能查到
- `timeout` 最大不能超过 15 秒，超过这个值设置无效
- 如果接口返回的不是 JSON，需要加 `dataType: 'text'`

第一次接入时最容易遇到的报错是 `Cloud API isn't enabled`，原因是 `init` 还没跑完就发起了调用。上面代码里等 300ms 重试最多三次的处理方式，基本能覆盖这种情况。👉 [用按量计费开通一个云托管环境试试](https://bit.ly/yunhuodong)

## 服务怎么部署上线？

部署有三种方式：控制台模板部署、GitHub 自动部署、CLI 命令行部署。选哪种取决于你迭代的频率。

第一次部署用控制台最省事：进入云托管后台，点「模版部署」，选一门熟悉的语言，输入数据库密码，点部署就完成了。它会自动生成一个服务，你可以在服务列表里看到服务名称。

需要持续迭代的话，把 GitHub 仓库和服务绑定，之后每次提交代码会自动部署。

如果不想每次开控制台，用官方的云托管 CLI 更顺手：

bash
# 安装
npm i -g @wxcloud/cli

# 登录，密钥在云托管控制台-设置-全局设置-CLI密钥生成
wxcloud login --appId <微信 AppId> --privateKey <秘钥>

# 项目初始化，自动生成容器文件
wxcloud migrate

# 部署
wxcloud deploy


配置好之后，每次发布只需要执行 `wxcloud deploy` 一条命令。部署完成后会返回访问地址，格式类似 `demo.ap-shanghai.run.tcloudbase.com`。

这里最容易被低估的是缓存问题。云托管没有 Redis，容器实例被回收后本地缓存也不可用，意味着每次调用都得实际消耗服务器和数据库资源。如果不额外购买缓存服务，高频接口的费用会很难看。

另一个坑是最小实例数。默认值是 0，没有用户访问一段时间后服务会完全停掉，这时候用户打开小程序，后端接口是调不通的。正式项目建议在「服务列表 - 服务设置 - 实例副本数」里把最小实例数设为 1。

代码质量也直接影响账单。按量计费模式下，一个死循环或者低效查询就能把资源消耗拉高。上线前把明显的性能问题清一遍，比事后优化便宜得多。👉 [查看云托管当前的套餐与活动价](https://bit.ly/yunhuodong)

## 常见问题

**调用时报 `Cloud API isn't enabled` 怎么办？**
这是 `init` 还没完成就发起了调用。等待 300ms 重试通常能解决，或者把 `init` 放在所有调用之前并 `await` 它完成。

**小程序提示基础库版本过低？**
去小程序管理后台把基础库最低版本设为 2.23.0 及以上，同时确认用户端微信版本不是太旧。

**云托管服务能访问外网吗？**
国内服务器访问外网受限，这是云托管的已知限制。如果业务需要抓取外网数据，可以加一层 Cloudflare Worker 之类的边缘转发服务，把「小程序 → 你的域名 → 外网」这条链路搭起来。前提是小程序能访问你的域名，所以域名本身要能正常解析。

**服务突然调不通了？**
先检查最小实例数是不是 0，服务可能因为长时间无访问被停掉了。设为 1 之后观察一段时间。如果仍然调不通，再看服务日志和部署版本是否正常。

**敏感配置放在哪里？**
不要写死在代码里。在「服务列表 - 服务设置 - 环境变量」里配置，线上修改后不需要重新部署。
